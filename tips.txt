nft list table inet cfm

(Use your real names, not legacy ones)

4) Verify DNAT edge mode (your OpenResty case)

nft list table inet cfm_redirect
nft list chain inet cfm_redirect prerouting
cfm dnat

If these are present and cfm dnat says ON, then dnat_edge is correct regardless of missing challenge_* sets.
5) Check whether “counter unavailable” warnings are FP

Those warnings usually mean the command expects named counters that may not exist in your current rules style.

Inspect flood/connlimit/portflood chains for counters:

nft -a list chain inet cfm flood
nft -a list chain inet cfm input
nft -a list chain inet cfm output

If rules exist and enforce correctly but named counters are absent, warning is likely FP (observability gap, not policy failure).

# ─── nftlib backend verification ────────────────────────────────────────────
#
# nftlib writes blocks, allows and blocklist feeds over netlink, with no nft
# subprocess. The self/port sets and the input-chain rules (ports policy, DNAT
# accepts) still go through the nft binary. The set/element contents are
# identical; only the write path changes.
# Use the same `nft list` commands to verify state (kernel is the ground truth).
#
# Switch to nftlib: set CFM_FIREWALL_ENGINE = "nftlib" in /etc/cfm/cfm.conf,
# then restart the daemon (it reads the engine only at startup). `cfm` CLI
# commands read the same key, so they run on nftlib too:
#   systemctl restart cfm
# The CFM_FIREWALL_ENGINE environment variable overrides cfm.conf for the one
# process it is set in, e.g. a one-off CLI test:
#   CFM_FIREWALL_ENGINE=nftlib cfm status
# Don't use `systemctl set-environment` for it: that changes only the daemon,
# and the CLI (reading cfm.conf) would then run the other engine.
#
# Confirm which engine the running daemon is using (logged at startup, before
# the log file is opened, so it lands in the service's stdout log):
grep -h 'firewall engine' /var/log/cfm/cfm-service.log* 2>/dev/null | tail -1
#
# Confirm nftlib is NOT spawning nft subprocesses during a block:
#   In one terminal, watch for nft forks:
strace -f -e trace=execve -p $(pgrep -f "cfm daemon") 2>&1 | grep nft
#   In another terminal, add a block. With nft engine you see "execve nft ...".
#   With nftlib engine: silence (no execve for nft).
#
# Same check with fork count — should stay flat with nftlib:
watch -n1 "cat /proc/$(pgrep -f 'cfm daemon' | head -1)/stat | awk '{print \"forks:\", \$10}'"
#
# Verify a block added via nftlib shows up in kernel state:
CFM_FIREWALL_ENGINE=nftlib cfm block 203.0.113.1 --ttl 5m
nft list set inet cfm block_v4 | grep 203.0.113.1
#
# Check a bulk feed loaded via nftlib (element count should match):
nft list set inet cfm block_ext_v4_hosts_dshield | wc -l
# Should be same count regardless of engine; nftlib just writes it faster.
#
# nftlib opens a netlink socket per kernel call and closes it again, so an
# idle daemon holds none; its call counts, errors and slow calls are in the
# `netlink` block of the firewall_selftest MCP tool.
#
# Debug nftlib netlink traffic (requires root):
nft monitor   # shows all kernel-side set/rule changes in real time
